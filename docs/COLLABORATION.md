# 项目内协作目录

通过 ACMS 添加项目（包括创建目标时同时建项目）会在项目根目录建立 `.acms/`。编辑已有项目或执行已有任务也会补建。目录写入失败时，界面明确提示“记录已保存，但协作文档更新失败”，不会伪称文档已创建。

- `README.md`：协作入口与交接规则。
- `shared.md`：所有者维护的长期约定和材料位置，系统仅首次创建，后续不覆盖。
- `project.json`：项目归属标记，防止不同 ACMS 项目覆盖同一个协作目录。
- `CURRENT.json`：最新快照的路径及内容哈希。
- `snapshots/<hash>.json`：目标、任务、父子关系、依赖、状态、阻塞、最近执行摘要和交付物索引。
- `evidence/<hash>.md|json`：迁移的文档原文和完整评论。任务索引保留旧任务编号、文档 key、更新时间及最近评论，可以在本地解析旧 Paperclip 文档链接。

系统不会让执行器一次读取全部历史材料。派发合同要求它先解析自己的任务、父任务和依赖，再按索引读取所需证据，优先复用最近检查点。历史文档是证据，不是新授权；旧批准记录也不会自动批准本轮新行为。

每次普通执行将当前目标的协作材料同步到隔离工作区 `.acms/context.json`、`shared.md` 和 `evidence/`，因此 Git 未提交文件也能传入。已有工作区重试时刷新上下文，不覆盖业务产物。审查使用作者执行时固定的版本，不读取随后变化的所有者说明。

`.acms` 是宿主管理的上下文输入。执行器应在普通任务目录写交接文档，并通过 ACMS 提交摘要、产物或阻塞；系统在执行结束后更新项目快照。阻塞返回中的 `reversibleDefault` 也作为未验收交接保留。不得直接改写固定上下文；提交和审查验收会校验哈希。

协作输入不计入业务改动集，也不会被自动合并到 Git。源项目其他未提交改动仍阻止自动合并。ACMS 不自动提交、清理或重置业务文件。目录和文件不允许通过符号链接重定向。

当前限制：快照不会自动携带源项目所有未提交的业务文件；`.acms` 只解决协作信息和历史证据的传递。实际缺失的外部材料或新的审批仍会使相应任务等待。
