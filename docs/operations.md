# 安装、使用和恢复

## 安装配置

使用 Node.js 24 和已初始化的 DSH profile。在仓库执行 `npm ci`、`npm run build` 后运行 `scripts/install.ps1`。可用参数：

| 参数 | 用途 |
|---|---|
| `-DshCommand` | `dsh.cmd` 路径，默认 D 盘 DSH 安装路径 |
| `-TargetProfile` | 已存在的 profile，默认 desktop |
| `-DshHomePath` | DSH_HOME；隔离测试应使用独立目录 |
| `-DataDirectory` | ACMS 公司数据库和工作副本目录，必须在源项目之外 |

通过 DSH 官方 plugin CLI 管理 bundles。不要手工修改 profile package.json。安装脚本备份已有 patch，并维护 `BEGIN ACMS MANAGED CONFIG` 到 `END ACMS MANAGED CONFIG` 区段。再次安装更新该区段。

独立 profile 的第一次创建可使用 DSH 的 `--from-default-profile web --dump-config` 功能。正式使用仍在 DSH 原生界面中完成。

## 模型列表与配对

修改代码后的部署：先暂停调度并等待在途工作结束，运行 `npm run build`，再在项目目录运行 `node scripts/deploy-live.mjs desktop`。DSH 默认仅监视配置文件，单纯修改宿主源码不会加载新代码。部署脚本生成版本化宿主 bundle，在构建前和切换 ACMS 入口前分别检查任务执行、对话、Git 集成及工作副本恢复状态。存在在途集成、待核对的清理或未完成的工作副本恢复时，按报错中的集成编号或恢复说明处理，再重新运行。
界面更新后按 Ctrl+R 刷新 DSH。部署产物 `host-<hash>.mjs` 按内容哈希引用同目录的 `owned-job-<hash>.cs`、`archive-worker-<hash>.mjs` 和 `bare-transaction-hook-<hash>.mjs`。部署和回滚时，先保留宿主及其匹配资源，再切换宿主入口。其他 profile 可替换最后的 `desktop`，自定义 home 使用 `DSH_HOME`。

切换前的配置保存在 `<dataDir>/install-backups/`，部署输出会打印本次备份路径。配置发布失败时保留切换前的入口。已切换后如需回退，先停止宿主，在备份中核对旧 ACMS 入口及对应宿主文件，再把该入口恢复到当前 profile，保留其他插件配置。涉及数据版本的回退按[发布检查清单](iteration-1-release-checklist.md)核对兼容性及备份。

初始模型列表仅包含 DSH 模型目录中的内部模型。内部模型可以选择是否继承 ACMS 调度父代理上下文，常规内部执行每轮新建上下文。外部模型不显示父代理继承开关。

外部模型使用“模型列表 → 配对外部 agent”：复制 prompt，交给目标 agent 生成本机运行入口，读取并确认回执后添加。之后 ACMS 自动启动该环境执行任务。详见 [配对协议与边界](external-models.md)。角色可以选择内部模型或已配对的外部模型。

外部执行当前只在 Windows 上提供已核实的进程容器：用系统 .NET Framework64（`v4.0.30319`）的 `csc.exe` 编译内置原生助手，通过命名管道下发控制消息，并用 Job Object 管理本次执行的进程树。它不是安装其他 DSH 插件，也不改变模型的 sandbox 与 approvalPolicy；非 Windows 会在启动模型前明确失败，不降级为按 PID 猜测。

页面只显示已有模型目录和缓存配置，打开页面、切换模型、读取配对回执都不调用模型。只有点击“检测模型连通性”才发送简短真实请求并读取配置。检测结果按模型和通道保存 10 分钟，失败的配置不能直接保存或派发，可重测恢复。内部模型支持时可设置思考深度；外部显示配对声明/runner 返回值，标注来源，未知值不猜测。

首次创建目标可同时填写项目名称和目录，不需要先创建任务。“选择目录”在 DSH 桌面调用系统目录选择器，其他环境提供目录浏览；也支持 Ctrl+V 或“粘贴路径”。任务详情提供“删除任务”，删除后进入回收站。活动执行、未完成清理和被依赖任务会显示具体阻止原因；恢复未完成任务时保持暂停，交付物与执行历史保留。

公司总览和任务工作台按“项目 → 目标 → 任务 → 子任务”展示，可展开、按目标进入工作台、通过任务详情的父任务链接返回。删除最后一个任务后，目标本身仍保留，明确标为“暂无任务”，不计入正在执行的目标数。

回收站支持“彻底删除”，需要输入任务标题确认；先解除关联或处理依赖任务。彻底删除会移除任务及关联审查、执行、验收和产物索引，无法从界面恢复；审计记录保留，本机工作副本、共享产物文件及源项目文件不自动清理。恢复与彻底删除是两个独立操作。

“常驻／临时人员”控制任务完成后是否还可分配工作；临时人员默认在短期任务完成后退出名单。任务可选择完成后保留临时执行人员。任务线程是否续接取决于所选执行入口声明的上下文能力：内部入口以运行时观测为准，外部配对入口以配对配置声明为准，未声明时不推断为支持。续接与人员留任（longLived）分开；同一任务用相同 contextKey 隔离重试和返工。每轮执行结束都会释放执行资源，历史任务、交付物与线程记录不自动删除；记录保留不等于自动续接。独立对话的历史只在对话内传递，不并入任务上下文，与任务线程续接分开描述。

## 日常操作

- 新建目标会立即进入规划。默认由负责人提交计划后自动派工；先填写明确范围及验收标准。
- “暂停公司”停止在途任务并暂停调度；“恢复调度”只解除公司级暂停，主动暂停的任务、目标级暂停、材料或预算阻塞以及未确认的清理仍需分别处理，详见下文[暂停、停止与恢复](#暂停停止与恢复)。
- 编辑任务与依赖需要任务处于可编辑状态；执行中的任务会先停止旧轮次，编辑立即保存，清理确认后按新要求继续。停止与清理的边界见下文。
- 项目、目标与任务默认收起；展开状态按对象记忆。已完成/归档/取消的目标与任务进入各自的“已完成”列表，主视图保留进行中任务和仍含未完成后代的父级。列表按最近有效业务活动倒序，执行进度和心跳不会把条目置顶。
- 缺少材料的分支会出现在总览“等待你的决定”，回答后自动重新调度。
- “公司设置”可为目标配置效率时间盒与收尾预留（毫秒，0 表示不启用）。到点后保存检查点并通知负责人，普通任务暂停派发；负责人决定收尾或调整范围后恢复。它与成本硬上限分开，不会自动新增预算交互；额度追加后旧的时间盒决策会清除，便于新窗口再次预警。
- 技术失败先重试，再创建修复任务；审查环境失败、重试耗尽、选模无候选、集成冲突等可恢复阻塞自动转给目标负责人协调，重复上报复用同一个协调任务。额度用尽、材料或权限缺口、负责人不可用、清理未确认时保留证据并要求所有者处理。审查未通过时同样由负责人决定返工范围，被审任务保持已交付状态。
- 审查被取消时不会自动重建：任务保持完成、目标保持进行中并显示取消原因、时间和操作者；在任务详情或目标详情点击“重新发起审查/重新发起最终审查”即可基于当前交付重建，同一交付最多一个进行中的审查，旧结论不会复用。
- 目标模板新版本默认只用于新目标；已有目标保留创建时固定的模板版本。

### 设置目标金额上限

新建目标时可填写可选的美元金额上限，精确到六位小数。留空的目标和既有目标继续使用原调度。金额授权从新目标创建开始，规划、实现、修复与审查的模型执行共用同一余额。目标详情显示预留、已收到回执的费用、可派发余额及等待结算状态。只有所有者的「追加金额上限」操作会增加金额授权。

执行前，已选路由必须由受信任的宿主执行器提供可执行的费用上界。ACMS 按执行尝试原子预留。已结束但缺少清理证明或最终费用的尝试继续占用原预留，待同一授权的证据核实后才结算或释放。金额账本随数据库保存，彻底清除任务也会保留该目标的费用及未结项。若执行器回执超过其承诺的上界，系统记录实际报告金额并停止该目标的后续派发。

内置 DSH 和已配对执行器暂未提供此上界契约。启用金额上限时，这些路由的任务会在模型启动前等待，调整金额也不会补足上界证据。token 用量、执行耗时和供应商订阅均不能代替这项证据。任务会话可排队或中断续接，续接需重新预留。

#### 开工前核对计划金额

启用金额上限且由负责人自动规划时，计划列出必做、可选、依赖和选模依据。受信任的宿主执行器提供逐任务估算与验收、返工的计划预留。提案保留估算来源、最低交付和完整范围的预计金额。计划使用提交时扣除已结算与所有在途预留的余额，尚未取得费用的规划调用也保留预留。

估算完整且覆盖最低交付时，ACMS 派发可负担的范围。预算只能覆盖必做时，可选任务延期。项目或模板要求人工批准时，仍由所有者在同一版本上批准。预计不足或缺估算时，提案保留且不会派发实现任务。可在目标详情追加金额并批准原范围、退回修改计划，或结束目标。原本延期的可选项仍留在原计划证据中。批准时再次核对余额、验收检查、模型配置及同一受信来源的报价。报价变化或无法核实时，原提案仍可查阅，需退回重新估算。

计划中的预留用于估算，实际费用继续按每次尝试的受信回执结算。内置 DSH 和配对执行器当前没有这项估算契约。金额上限未启用的目标和明确采用手工派工的目标沿用原流程。

#### 查看预计完工成本

在「目标金额上限」中选择「查看完工估算」，或从所有者界面调用 `GET /api/acms/cost/forecast?goalId=…`。快照将独立账本中的已结算费用、尚未结算的执行上界、当前批准版本中未开始任务的估算，以及仍能核对为未用的验收和返工计划预留相加。已有对应执行预留的任务不会重复加入未开始小计。已收到零费用回执、明确估算为零、缺少费用或估算证据分别显示。

已清理执行的费用回执仍未到达，或者报价、任务或合同变化及重试造成剩余金额无法核对时，快照显示有证据的分项及覆盖范围，完工总额和预算余裕保留未知。原计划的验收和返工金额仍可核对，阶段已推进且无法分拆时会明确标记剩余未知。同一批准范围已完整交付且费用已结清时，完工费用以实际回执为准，历史报价仍可追溯。完工预算余裕使用该次快照里的授权上限。结算账本随备份保留，彻底清除单项任务也不影响账本上的历史费用。刷新估算只读取当前范围，派发依然按每次执行授权。

#### 运行中为必做任务保留余量

金额受限计划中的未开工可选任务，实际派发前会按当前余额、这次执行的可信费用上界、仍未支付的必做估算以及已批准的验收和返工预留核对。已经预留的执行上界在账本中只占用一次。仍有待结算费用时，原预留继续占用余额。可选项因此等待期间，其他可派发的必做任务按原规则运行；若某项已成为仍需完成工作的前置任务，该项沿用必做路径。费用释放后会重新核对等待项，也可在目标金额面板选择「重新核对报价」启动一次新核对。

余额确认不足且相关可选任务及其后续均未开始、没有独立阻塞时，所有者可在同一面板确认本轮延期并填写理由。确认会重新核对余额、计划、最近一次核价和依赖范围，并留下审计。已延期任务保留为历史，本轮仅对剩余交付按原验收执行检查与最终审查。再次安排已延期工作需要创建新任务。验收和返工尚无逐阶段费用余额时，派发门禁保留原计划预留。任何变化仍受逐次上界和所有者授权金额约束。

### 查看任务模型用量

在目标详情选择「查看执行用量」，可查看整个目标或指定任务的已保留执行记录。完整小计和覆盖数量包含所选范围的所有保留记录，逐次列表仍单独显示本页小计。按路由可查看已经确认的执行通道、模型及已知思考深度。按日期使用每次执行开始的 UTC 日期，日期或路由证据不足时单列未知。执行前检查未通过、尚待结束或清理核对、终态未提供可靠数据分别显示。供应商明确报告的 0 会保留，未报告的字段显示「未知」。彻底删除任务会随其执行记录更新汇总。

当前记录由配对 Codex app-server 报告，并随本次执行的结束及进程清理回执保存。每条 Codex 用量事件都区分最新增量和整个线程累计。界面显示截至本轮终态、能明确归属本轮的已上报增量。续接时，只有在发出新一轮前收到同一线程可信的旧用量基线，并能核对本轮增量时，才显示本轮用量。普通配对、缺少证据的 DSH 执行和历史记录保留未知。缓存及推理 token 作为供应商明细单列，合计沿用供应商报告值。相关语义见 [Codex 事件转发](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/src/bespoke_event_handling.rs#L1594-L1610) 和 [OpenAI 的 Codex 用量说明](https://github.com/openai/symphony/blob/main/elixir/docs/token_accounting.md)。

本页覆盖 ACMS 任务执行。外部对话、监控和连通性检测属于此范围之外。累计执行时间、供应商订阅额度、估算费用和实际账单各有独立口径。

所有者宿主也可读 `GET /api/acms/usage?goalId=<目标 ID>` 或 `GET /api/acms/usage?taskId=<任务 ID>`。默认每页 30 条，可用 `limit` 请求 1 至 100 条，下一页将返回的 `nextBefore` 传给 `before`。汇总按该页受支持的字段分别计算，未知字段的小计为 `null`，明确为零的小计为字符串 `"0"`。

完整范围使用 `GET /api/acms/usage/summary` 并指定相同的 `goalId` 或 `taskId`。顶层覆盖和小计始终包含该范围的全部保留记录。分组可设为 `groupBy=route`（默认）或 `groupBy=date`，后者返回 `dateBasis=started-at-utc`。每页默认 20 组，`limit` 上限 100，下一页把 `nextAfter` 原样传给 `after`。路由按固定长度的指纹排序，日期按 UTC 从新到旧排序，未知组排在最后。

提供 `attemptBefore` 时，汇总还返回同一读取快照中的 `attemptPage`，含最多 30 条逐次记录，字段和逐次接口一致。最新页传入 `9007199254740991`，更早一页传入返回的 `attemptPage.nextBefore`。目标面板的主动查询同时更新完整小计、分组和逐次页。

### 批准计划后派工

在「公司设置 → 项目与检查」编辑项目，或发布目标模板时，可以要求所有者批准计划后派工。新建目标时，项目或所选模板任一启用即生效。之后修改开关或发布新版模板，已经创建的目标保留其审批要求。

负责人提交计划后，在「公司总览 → 等待你的决定」或目标详情可以查看交付范围、取舍、拟派发任务及其依赖。此时规划进程结束，清理确认后释放执行槽；此目标的执行与返工等待，其他目标照常调度。填写理由后可批准、拒绝或退回修改。批准将当前版本及其任务依赖一次性入库；拒绝保留决定并继续等待，之后可重新规划。退回会开启新一代规划，并把理由交给负责人。待批期间更改目标验收要求，旧提案作为历史保留，新计划需重新批准。目标可暂停或取消；要暂停规划本身，也可在任务详情操作。

审批记录保留提案版本、规划代次、目标合同和所有者决定，可在目标详情和动态日志核对。项目或目标从回收站恢复后，恢复暂停的规划任务即可继续处理仍然有效且清理已确认的提案。计划审批只控制派工，项目已有的检查、交付方式和目标最终审查设置照常生效。

## 暂停、停止与恢复

暂停、停止与恢复作用于不同层级，不能互相替代。停止在途执行只请求终止本次执行；任务通常先进入 `stopping`，清理确认后才变为 `paused` 或 `cancelled`。

- **暂停公司**（`company.pause`）：立即暂停时停止所有在途任务（执行、审查、集成）并阻止新派发；带 `afterCurrent=true` 时允许当前执行和集成自然结束，只阻止后续派发（`pauseMode` 为 `after-current`）。立即暂停时有在途执行的任务先进入 `stopping`，清理确认后才变为 `paused`。
- **停止在途执行**：取消任务、单任务暂停、公司立即暂停或目标立即暂停都会向本次执行拥有的进程树发出停止请求。有在途执行的任务先进入 `stopping`；只有取得清理确认后才按停止意图变为 `cancelled` 或 `paused` 并释放执行占位。目标级 `afterCurrent` 暂停是例外：已完成的结果先暂存并把任务置为 `paused`，该次执行清理尚未确认时仍保留资源占位。无法确认清理时保持 `reconciling` 和资源占位，不重新派发、不自动修复，只能“重新读取回执”，不能删除锁、改数据库或手工释放占位。
- **恢复调度**（`company.resume`）：解除公司级暂停并允许新派发；不会解除目标级暂停、单任务暂停、材料或预算阻塞，也不会跳过未确认的清理。
- **单任务暂停**（`task.pause`）：暂停指定任务，并默认级联暂停该任务的审查子任务；运行中的任务先停止在途执行并等待清理确认。仅用户可恢复主动暂停的任务（`task.resume`），恢复后按当前合同重新派发；`task.retry` 是重试计数重置，不属于暂停语义。
- **目标级暂停**（`goal.pause`、`goal.resume`、`goal.cancel`）：立即暂停停止该目标的在途任务，未完成的结果不会入库；`afterCurrent=true` 时允许当前执行自然结束，已完成结果暂存（`resultDeferred`），恢复目标后再入库。取消目标会丢弃暂存结果并取消任务。恢复目标只解除目标级暂停，其他暂停、阻塞和未确认清理继续生效。

公司级、目标级和任务级暂停叠加时，任一层未解除都不会派发。清理未确认的 `reconciling` 占位优先于恢复调度。

源项目应先提交初始 Git 版本。关闭自动合入时，Git 项目的任务详情会显示交付提交、源基准和本机 Git 交付包。选择自动集成前明确该项目的验收检查。

对于需要完整可运行版本的 Git 目标，所有者可在新建目标时勾选「生成完整 Git 候选」。项目需关闭自动合并，并配置至少一项验收检查。首次执行工作任务时固定源提交。下游读取已选依赖的持久版本，目标的联合检查和可选最终审查使用同一候选。完整候选的提交和本机交付包可在目标的最终审查区查看。

独立目录副本项目可以选「生成完整目录候选」。首次执行时冻结源目录的受控文件及目录结构，之后任务使用该基线和已选依赖版本。工作副本改动按路径组合，两个版本在同一位置有不同改动时会报告冲突。目录候选沿用项目检查和最终审查，候选内容指纹显示在目标的最终审查区。备份时保留 `deliveries/copy/` 和登记副本内的受控空目录。缺失的持久文件会阻止组合和联检。与普通目录副本一样，依赖缓存、协作数据和凭据路径不纳入项目文件。

完整候选通过联合检查并满足模板审查要求后，可在目标详情「最终审查」下载候选 ZIP。Git 和目录目标都按已验收的持久版本生成归档。将 ZIP 内的 `source/` 解压到空目录即可得到该版源码。见[完整交付归档校验](delivery-archives.md)。

关闭自动合并的完整 Git 候选还可以在「最终审查 → 创建 Git 交付分支」选择作为基准的本地分支。预览显示候选版本、合同、基准 HEAD、变更、验收证据，以及 ACMS 分配的新分支名。所有者确认后，Git 在同一引用事务中验证基准 HEAD 并创建该交付分支。创建只写入新的引用，现有分支、索引和工作副本均保留。基准树已变化或分配的新分支被占用时，请按提示重新预览或联合核验候选。Git 操作已开始时，撤回请求会等待实际结果。若出现「等待核对 Git 结果」，可在相同入口请求复核。

项目设置可选授权独立的本机裸 Git 交付仓库。该仓库使用 `files` 引用格式和支持硬链接的文件系统，需要有已存在的目标分支，平时通过克隆或推送使用。项目的执行目录仍是原来的 Git 工作副本。候选达到相同的验收要求后，所有者可在「交付 Git 候选」选择「更新裸交付仓库中的现有分支」。预览会显示已授权仓库、目标分支和旧 HEAD。确认后，Git 仅在该分支仍指向预览 HEAD 时把它快进到候选树。源项目及其他分支保留原状。目标树与候选基线不一致时，需要基于目标内容重新生成并核验候选。

裸仓库若在使用登记工作副本或默认索引，请等相关 Git 操作完成，或另用独立裸仓库。配置了自定义引用或推送策略的仓库继续使用原仓库的流程。宿主在执行时只暂时占用自己的 Git 登记名和默认索引锁，收到进程清理回执后才释放。目标目录身份变更时，请恢复原目录进行核对。需要授权新的裸仓库时，可在项目设置中先清除旧路径，再选择该仓库。

旧的「自动合并」设置在单项任务通过自身交付检查和隔离合并检查后更新源 Git 分支。模板配置的最终审查在任务交付后安排。

### 批准交付后合入

在项目设置或发布的目标模板开启「新目标须经所有者批准交付后合入」。该设置与计划派工审批独立。新目标自动使用完整 Git 候选，需要关闭自动合入并至少配置一项项目验收检查。旧目标继续使用创建时的审批设置。

候选通过联合检查和模板要求的最终审查后，从「公司总览 → 等待你的决定」进入「人工交付审批」。选择项目仓库中的新交付分支，或已授权裸交付仓库中的现有分支。预览列出候选版本、合同、检查、审查、变更与目标 HEAD。填写理由并批准后，宿主再次核对候选和仓库授权，并由 Git 按已预览的 HEAD 单次更新指定引用。执行暂停、撤回、进程清理及重启后的结果核对沿用候选交付流程。

拒绝关闭该预览，之后可以显式预览其他交付选择。退回修改会阻止这一候选版本继续交付，即使改选分支或重新运行检查。请编辑需要修改的交付任务并重新执行；退回理由会送交后续执行者。新候选完成检查及所需审查后，可重新预览和审批。历次决定和对应目标保留在目标详情和动态日志。

当前人工交付审批支持完整 Git 候选。现有自动合入无法与此门禁同时使用；需要原地更新已检出的普通项目分支时，可沿该仓库流程处理新交付分支。

完整候选要求入选任务的 Git 交付覆盖工作副本。缺少证明时保留原交付和副本，需核对并补齐运行材料。父任务收到新的依赖版本时，只更新仍与旧输入一致的文件。遇到草稿或暂存冲突时保留已有内容。经合同评估获批的替代任务可读取自己的历史版本，最终候选选用当前交付。

有冲突、材料缺失或联合检查失败时，请查看目标和相关任务的集成状态。所有工作任务已交付后，目标合同或项目检查变化会使原验收过期。使用目标上的「重新联合检查」或所有者命令 `goal.composition.recheck`，可用当前已选交付核验并继续。检查使用现有集成资源及清理回执。

要从交付包重建，先用 `Get-FileHash -Algorithm SHA256` 对照任务详情中的包摘要，再把包检出到新目录。以下 PowerShell 命令保留交付提交中记录的原始文件字节。

```powershell
git clone --no-checkout --branch delivery -- <bundle> <newDir>
'* -text -eol -ident -filter -working-tree-encoding' | Set-Content -Encoding ascii -LiteralPath '<newDir>/.git/info/attributes'
git -C <newDir> -c core.autocrlf=false checkout --detach <deliveryCommit>
```

交付包位于数据目录的 `deliveries/`，包括该任务的 Git 源码树和已声明产物。整库备份包含交付包，恢复时会迁移其记录路径。仅凭交付包即可重建此次交付。
稀疏检出导致基准文件缺失时，任务会等待恢复完整检出并重新交付。

## 旧阶段制数据备份与隔离

旧版本把任务推进到工作流阶段（含强制审查）。升级到目标模板模型前，先运行备份工具导出旧数据并隔离：

```powershell
node scripts/legacy-export.mjs --data-dir <dataDir>            # 只备份，不改状态
node scripts/legacy-export.mjs --data-dir <dataDir> --apply    # 备份后归档旧任务/目标
```

备份写入 `<dataDir>/legacy/legacy-<时间戳>/`，包含一致性数据库快照 `company.db`、逻辑导出 `entities.json` 和 SHA256 清单 `manifest.json`。`--apply` 会把旧任务与目标标记为 `legacyBatch` 并归档，使其不参与新调度和目标完成计算，历史状态与证据不被改写。

自动迁移在宿主启动时、拿到调度租约之后、恢复执行之前进行：先对旧 attempt 逐条调用执行器恢复回执，只有确认 `cleanupConfirmed` 的才归档并释放名额；任何执行无法确认停止时**不修改数据库并阻止新调度启动**，保留旧数据供人工处理。此时请停止旧宿主、确认或清理旧进程后重试；若明确接受未确认状态，可运行 `node scripts/legacy-export.mjs --data-dir <dataDir> --apply --force`。另一宿主持有调度租约时不会先迁移再报错。日后恢复使用同一批次的 `company.db`，不要手工改运行数据库。

## 备份、恢复与保留

本机受控入口（源项目 Git 仓库仍单独处理）：

```powershell
node scripts/backup.mjs --data-dir <dataDir>                 # 只输出计划，不写文件
node scripts/backup.mjs --data-dir <dataDir> --out <backupDir> --apply
node scripts/backup.mjs --verify <backupDir>
node scripts/restore-backup.mjs --backup <backupDir> --target <emptyDir>
node scripts/restore-backup.mjs --target <restoredDir> --resume-worktrees
node scripts/prune-data.mjs --data-dir <dataDir> --days 30   # 保留 dry-run，不删除
```

- 数据库使用 SQLite `VACUUM INTO` 生成一致性快照（覆盖 WAL），并做 `integrity_check`；计划中的空间需求包含数据库快照估算（主库 + WAL），并按目标卷可用空间判断。其余文件按原始字节 SHA-256 写入 `backup-manifest.json`，`--verify` 会做全量遍历，检查大小、摘要、数据库完整性、多余文件与符号链接。raw-byte SHA-256 与 ACMS 的 `artifact.hash`（Base64 文本摘要）不能互换。
- 默认排除可重建目录 `node_modules`、`.git` 目录、`.cache`、`diagnostics`；只排除数据目录顶层的 `company.db`/`-wal`/`-shm`（由一致快照替代），历史备份目录或交付物中嵌套的 `company.db` 会正常备份。关联 worktree 的 `.git` 指针文件会保留，备份清单另记录 Git 登记、提交和暂存索引证据。依赖目录按 `REBUILD.md` 运行 `npm ci` 重建。排除项在清单和恢复生成的 `REBUILD.md` 中带重建方法。`pairing/` 含外部配对 runner 信息，默认不进入备份，需在新环境重新配对（`--include-pairing` 需所有者自行评估敏感性）。`conversations/` 与 `artifacts/` 可能包含私有内容，计划阶段会明确告警。
- 恢复目标必须是空目录；脚本先校验清单再复制，拒绝覆盖已有数据。恢复时会把数据库实体中指向旧数据目录的绝对路径（任务工作副本、artifact blob 等）改写为新目录，并更新恢复清单；数据库外的项目源路径保持不变。恢复后的在途执行进入 `reconciling`，只能“重新读取回执”，不要重跑、删除锁或改数据库；配对与依赖按 `REBUILD.md` 重建。历史事件/命令文本中的旧路径作为审计记录保留，不改写。
- Git 工作副本需要额外核对。停止旧宿主，将仍占用原路径的工作副本移到保留位置，并保留源仓库及其中的 worktree 登记。恢复脚本核对原指针、提交树、暂存对象及在途 Git 回执后，将 Git 登记连同暂存索引迁移到恢复副本的独立路径。旧工作副本的文件和 `.git` 指针原样保留，旧指针在迁移后无法再连接新索引。源仓库工作树和提交仍按原样保留。
- 文件复制完成而 Git 核对待处理时，恢复命令退出码为 2，JSON 返回 `startable: false`，宿主也会阻止启动。按 `REBUILD.md` 指出的路径处理旧工作副本或恢复原源仓库，然后对同一目标使用 `--resume-worktrees`。旧备份缺少登记证据时，从原环境重新生成含 Git 登记证据的备份。
- `prune-data.mjs` 只做 dry-run：按目录树内最新修改时间（跳过可重建的 `node_modules`/`.git`）列出超过保留期限的 `workspaces/`、`reviews/`、`integration/`、`diagnostics/` 副本及空间；仍被未完成任务、运行中执行、待清理占位或在途集成的 task/integration ID 引用的目录会标记保护，不会出现在可清理列表。只读打开 WAL 数据库后，SQLite 可能在数据目录留下 `-shm/-wal` 辅助文件（例如 32 KiB 的 `-shm` 与 0 B 的 `-wal`）；业务数据不被修改。实际删除仍由所有者按现有授权流程执行。
- Git 工作副本进入可清理列表前，需要核对当前登记的交付包、索引和从包独立重建后匹配的工作区指纹，并排除在用的审查或依赖。缺少交付包的旧记录、包损坏或存在额外未提交成果时，计划显示保护原因。
- 备份与恢复目标都会用 realpath 检查，拒绝备份目标位于数据目录内或恢复目标位于备份目录内。备份为整文件读入内存（单个文件大小未额外限制，超大文件会占用等量内存），不保留原始 mtime/文件模式；恢复后的文件按私有内容权限写入。首版仅支持当前本机数据目录，不包含云备份、跨设备同步、源项目仓库、认证文件或外部模型配对令牌。

## 异常恢复

### Git 集成

自动合入使用 Windows Job Object。缺少已验证的进程容器时，自动合入在启动 Git 集成命令前停止。

- 排队中的任务可直接暂停或取消。候选准备或检查已经开始时，立即暂停、取消和宿主关闭会请求停止自有进程树。清理确认后才释放占位。优雅暂停允许当前集成完成，并暂停接续调度。
- 最终 fast-forward 启动前核对任务代次、停止意图、租约、项目授权、目标分支和 HEAD。命令启动后等候有界结果。Git 已合入时，任务记录实际提交与同期停止请求。
- 重启时用持久集成记录、进程清理回执及 Git 分支历史核对实际结果。若证据不足，任务进入“核对中”，可用“重新读取回执”再次检查。确认已合入的提交直接补录，保留当前 Git 内容。

### 模型执行

`reconciling` 表示旧执行或副作用尚不能确认。任务详情“核对中断执行”里的操作是“重新读取回执”：它按该次执行的完整身份重读 `<dataDir>/paired-runs/` 下的逐次回执，不释放未知占用，也不派发新执行。身份由 provider、model、attemptId、contextKey、generation、kind、persistent 和 runtime 组成；回执为 `<runKey摘要>.json`，执行锁为同名 `.json.lock`。进程是否存活、根进程是否退出或宿主是否重启，都不能代替清理确认。

- 身份全部匹配、终态 `completed`、结果完整、清理已确认且没有锁：恢复已有结果并按原验收与收集流程入库，不再次调用模型。
- 身份匹配、终态 `stopped`、清理已确认、没有完整结果且没有锁：允许按现有调度重试。
- 执行中、锁仍存在或无法读取、清理未确认、回执缺失或损坏、身份错配、终态矛盾：继续保持 `reconciling` 和资源占位，不自动重试、不自动修复。
- 完成回执已写入但业务入库中断：先按回执补完入库，不重复执行。

人工查看日志和工作副本只用于定位问题。没有“人工勾选已停止即释放占位”的入口；不要删除锁、改数据库状态或清理 `paired-runs` 来绕过核对。旧版本执行缺少完整身份和逐次回执时无法由 contextKey 推测结果，缺失回执也按未知处理，不因宿主重启或进程已退出而放宽。手动检测和聊天同样逐次留回执，尚无独立处置入口，未知时只能保守保持。

若主机权限导致 Windows Codex 工具初始化失败，检查专用 CODEX_HOME、运行身份和 Codex 沙箱环境；ACMS 会记录错误，但不会自行提升系统权限。

候选合并失败时，源项目保持不变。查看任务阻塞与保留的 candidate 目录；修复项目冲突、调整范围或检查后恢复。当前版本不会自动替所有者选择有歧义的合并策略。

更新源码时先暂停执行再重启宿主；不要在真实任务运行中覆盖 provider 核心文件。UI 修改后重新 build 并刷新 DSH。

## 卸载

```powershell
pwsh -File .\scripts\uninstall.ps1 -TargetProfile desktop
```

可用参数：

| 参数 | 用途 |
|---|---|
| `-DshCommand` | `dsh.cmd` 路径，默认 D 盘 DSH 安装路径 |
| `-TargetProfile` | 已存在的 profile，默认 desktop |
| `-DshHomePath` | DSH_HOME；隔离测试应使用独立目录 |

先暂停任务再卸载。脚本移除插件注册和 ACMS 配置块，保留数据库、项目分支、交付物与认证。删除运行数据必须另行核对，不属于卸载默认行为。
