# 安装、使用和恢复

## 安装配置

使用 Node.js 24 和已初始化的 DSH profile。在仓库执行 `npm ci`、`npm run build` 后运行 `scripts/install.ps1`。可用参数：

| 参数 | 用途 |
|---|---|
| `-DshCommand` | `dsh.cmd` 路径，默认 D 盘 DSH 安装路径 |
| `-TargetProfile` | 已存在的 profile，默认 desktop |
| `-DshHomePath` | DSH_HOME；隔离测试应使用独立目录 |
| `-DataDirectory` | ACMS 公司数据库和工作副本目录，必须在源项目之外 |

通过 DSH 官方 plugin CLI 管理 bundles。不要手工修改 profile package.json。安装脚本备份已有 patch，并维护 `BEGIN ACMS MANAGED CONFIG` 到 `END ACMS MANAGED CONFIG` 区段。再次安装更新该区段。

独立 profile 的第一次创建可使用 DSH 的 `--from-default-profile web --dump-config` 功能。正式使用仍在 DSH 原生界面中完成。

## 模型列表与配对

修改代码后的部署：先运行 `npm run build`，再在项目目录运行 `node scripts/deploy-live.mjs desktop`。DSH 默认仅监视配置文件，单纯修改宿主源码不会加载新代码；部署脚本会生成版本化宿主 bundle、备份配置，并仅切换 ACMS 的宿主入口，其他插件不受影响。存在活动 ACMS 执行时脚本拒绝部署。
界面更新后按 Ctrl+R 刷新 DSH。部署产物是 `host-<hash>.mjs`，它按内容哈希引用同目录的 `owned-job-<hash>.cs` 和 `archive-worker-<hash>.mjs`；部署和回滚必须保留宿主及其匹配资源，再切换宿主入口。其他 profile 可替换最后的 `desktop`，自定义 home 使用 `DSH_HOME`。

初始模型列表仅包含 DSH 模型目录中的内部模型。内部模型可以选择是否继承 ACMS 调度父代理上下文，常规内部执行每轮新建上下文。外部模型不显示父代理继承开关。

外部模型使用“模型列表 → 配对外部 agent”：复制 prompt，交给目标 agent 生成本机运行入口，读取并确认回执后添加。之后 ACMS 自动启动该环境执行任务。详见 [配对协议与边界](external-models.md)。角色可以选择内部模型或已配对的外部模型。

外部执行当前只在 Windows 上提供已核实的进程容器：用系统 .NET Framework64（`v4.0.30319`）的 `csc.exe` 编译内置原生助手，通过命名管道下发控制消息，并用 Job Object 管理本次执行的进程树。它不是安装其他 DSH 插件，也不改变模型的 sandbox 与 approvalPolicy；非 Windows 会在启动模型前明确失败，不降级为按 PID 猜测。

页面只显示已有模型目录和缓存配置，打开页面、切换模型、读取配对回执都不调用模型。只有点击“检测模型连通性”才发送简短真实请求并读取配置。检测结果按模型和通道保存 10 分钟，失败的配置不能直接保存或派发，可重测恢复。内部模型支持时可设置思考深度；外部显示配对声明/runner 返回值，标注来源，未知值不猜测。

首次创建目标可同时填写项目名称和目录，不需要先创建任务。“选择目录”在 DSH 桌面调用系统目录选择器，其他环境提供目录浏览；也支持 Ctrl+V 或“粘贴路径”。任务详情提供“删除任务”，删除后进入回收站。活动执行、未完成清理和被依赖任务会显示具体阻止原因；恢复未完成任务时保持暂停，交付物与执行历史保留。

公司总览和任务工作台按“项目 → 目标 → 任务 → 子任务”展示，可展开、按目标进入工作台、通过任务详情的父任务链接返回。删除最后一个任务后，目标本身仍保留，明确标为“暂无任务”，不计入正在执行的目标数。

回收站支持“彻底删除”，需要输入任务标题确认；先解除关联或处理依赖任务。彻底删除会移除任务及关联审查、执行、验收和产物索引，无法从界面恢复；审计记录保留，本机工作副本、共享产物文件及源项目文件不自动清理。恢复与彻底删除是两个独立操作。

“常驻／临时人员”控制任务完成后是否还可分配工作；临时人员默认在短期任务完成后退出名单。任务可选择完成后保留临时执行人员。任务线程是否续接取决于所选执行入口声明的上下文能力：内部入口以运行时观测为准，外部配对入口以配对配置声明为准，未声明时不推断为支持。续接与人员留任（longLived）分开；同一任务用相同 contextKey 隔离重试和返工。每轮执行结束都会释放执行资源，历史任务、交付物与线程记录不自动删除；记录保留不等于自动续接。独立对话的历史只在对话内传递，不并入任务上下文，与任务线程续接分开描述。

## 日常操作

- 新建目标会立即进入规划和执行；先填写明确范围及验收标准。
- “暂停公司”停止在途任务并暂停调度；“恢复调度”只解除公司级暂停，主动暂停的任务、目标级暂停、材料或预算阻塞以及未确认的清理仍需分别处理，详见下文[暂停、停止与恢复](#暂停停止与恢复)。
- 编辑任务与依赖需要任务处于可编辑状态；执行中的任务会先停止旧轮次，编辑立即保存，清理确认后按新要求继续。停止与清理的边界见下文。
- 项目、目标与任务默认收起；展开状态按对象记忆。已完成/归档/取消的目标与任务进入各自的“已完成”列表，主视图保留进行中任务和仍含未完成后代的父级。列表按最近有效业务活动倒序，执行进度和心跳不会把条目置顶。
- 缺少材料的分支会出现在总览“等待你的决定”，回答后自动重新调度。
- “公司设置”可为目标配置效率时间盒与收尾预留（毫秒，0 表示不启用）。到点后保存检查点并通知负责人，普通任务暂停派发；负责人决定收尾或调整范围后恢复。它与成本硬上限分开，不会自动新增预算交互；额度追加后旧的时间盒决策会清除，便于新窗口再次预警。
- 技术失败先重试，再创建修复任务；审查环境失败、重试耗尽、选模无候选、集成冲突等可恢复阻塞自动转给目标负责人协调，重复上报复用同一个协调任务。额度用尽、材料或权限缺口、负责人不可用、清理未确认时保留证据并要求所有者处理。审查未通过时同样由负责人决定返工范围，被审任务保持已交付状态。
- 审查被取消时不会自动重建：任务保持完成、目标保持进行中并显示取消原因、时间和操作者；在任务详情或目标详情点击“重新发起审查/重新发起最终审查”即可基于当前交付重建，同一交付最多一个进行中的审查，旧结论不会复用。
- 目标模板新版本默认只用于新目标；已有目标保留创建时固定的模板版本。

## 暂停、停止与恢复

暂停、停止与恢复作用于不同层级，不能互相替代。停止在途执行只请求终止本次执行；任务通常先进入 `stopping`，清理确认后才变为 `paused` 或 `cancelled`。

- **暂停公司**（`company.pause`）：立即暂停时停止所有在途任务（执行、审查、集成）并阻止新派发；带 `afterCurrent=true` 时允许当前执行和集成自然结束，只阻止后续派发（`pauseMode` 为 `after-current`）。立即暂停时有在途执行的任务先进入 `stopping`，清理确认后才变为 `paused`。
- **停止在途执行**：取消任务、单任务暂停、公司立即暂停或目标立即暂停都会向本次执行拥有的进程树发出停止请求。有在途执行的任务先进入 `stopping`；只有取得清理确认后才按停止意图变为 `cancelled` 或 `paused` 并释放执行占位。目标级 `afterCurrent` 暂停是例外：已完成的结果先暂存并把任务置为 `paused`，该次执行清理尚未确认时仍保留资源占位。无法确认清理时保持 `reconciling` 和资源占位，不重新派发、不自动修复，只能“重新读取回执”，不能删除锁、改数据库或手工释放占位。
- **恢复调度**（`company.resume`）：解除公司级暂停并允许新派发；不会解除目标级暂停、单任务暂停、材料或预算阻塞，也不会跳过未确认的清理。
- **单任务暂停**（`task.pause`）：暂停指定任务，并默认级联暂停该任务的审查子任务；运行中的任务先停止在途执行并等待清理确认。仅用户可恢复主动暂停的任务（`task.resume`），恢复后按当前合同重新派发；`task.retry` 是重试计数重置，不属于暂停语义。
- **目标级暂停**（`goal.pause`、`goal.resume`、`goal.cancel`）：立即暂停停止该目标的在途任务，未完成的结果不会入库；`afterCurrent=true` 时允许当前执行自然结束，已完成结果暂存（`resultDeferred`），恢复目标后再入库。取消目标会丢弃暂存结果并取消任务。恢复目标只解除目标级暂停，其他暂停、阻塞和未确认清理继续生效。

公司级、目标级和任务级暂停叠加时，任一层未解除都不会派发。清理未确认的 `reconciling` 占位优先于恢复调度。

源项目应先提交初始 Git 版本。默认保留交付分支，可从产物和任务工作副本查看输出；选择自动集成前明确该项目的验收检查。

## 旧阶段制数据备份与隔离

旧版本把任务推进到工作流阶段（含强制审查）。升级到目标模板模型前，先运行备份工具导出旧数据并隔离：

```powershell
node scripts/legacy-export.mjs --data-dir <dataDir>            # 只备份，不改状态
node scripts/legacy-export.mjs --data-dir <dataDir> --apply    # 备份后归档旧任务/目标
```

备份写入 `<dataDir>/legacy/legacy-<时间戳>/`，包含一致性数据库快照 `company.db`、逻辑导出 `entities.json` 和 SHA256 清单 `manifest.json`。`--apply` 会把旧任务与目标标记为 `legacyBatch` 并归档，使其不参与新调度和目标完成计算，历史状态与证据不被改写。

自动迁移在宿主启动时、拿到调度租约之后、恢复执行之前进行：先对旧 attempt 逐条调用执行器恢复回执，只有确认 `cleanupConfirmed` 的才归档并释放名额；任何执行无法确认停止时**不修改数据库并阻止新调度启动**，保留旧数据供人工处理。此时请停止旧宿主、确认或清理旧进程后重试；若明确接受未确认状态，可运行 `node scripts/legacy-export.mjs --data-dir <dataDir> --apply --force`。另一宿主持有调度租约时不会先迁移再报错。日后恢复使用同一批次的 `company.db`，不要手工改运行数据库。

```text
<dataDir>/artifacts/           按内容标识的交付副本
<dataDir>/workspaces/          任务隔离工作副本

<dataDir>/integration/         合并候选与失败诊断现场
<dataDir>/integration-receipts/ 集成命令的进程树清理回执

```

备份前暂停执行（最好关闭宿主）再复制数据目录和项目 Git 仓库。SQLite 正在运行时，不要只复制 company.db 而忽略 WAL；受控入口见下一节。公司资料与模型输出可能包含项目私有内容，只在本地运行目录保存。

## 备份、恢复与保留

本机受控入口（源项目 Git 仓库仍单独处理）：

```powershell
node scripts/backup.mjs --data-dir <dataDir>                 # 只输出计划，不写文件
node scripts/backup.mjs --data-dir <dataDir> --out <backupDir> --apply
node scripts/backup.mjs --verify <backupDir>
node scripts/restore-backup.mjs --backup <backupDir> --target <emptyDir>
node scripts/prune-data.mjs --data-dir <dataDir> --days 30   # 保留 dry-run，不删除
```

- 数据库使用 SQLite `VACUUM INTO` 生成一致性快照（覆盖 WAL），并做 `integrity_check`；计划中的空间需求包含数据库快照估算（主库 + WAL），并按目标卷可用空间判断。其余文件按原始字节 SHA-256 写入 `backup-manifest.json`，`--verify` 会做全量遍历，检查大小、摘要、数据库完整性、多余文件与符号链接。raw-byte SHA-256 与 ACMS 的 `artifact.hash`（Base64 文本摘要）不能互换。
- 默认排除可重建目录 `node_modules`、`.git` 目录、`.cache`、`diagnostics`；只排除数据目录顶层的 `company.db`/`-wal`/`-shm`（由一致快照替代），历史备份目录或交付物中嵌套的 `company.db` 会正常备份。git worktree 的 `.git` 指针文件会保留，恢复后工作副本仍可作为 git 仓库继续执行；依赖目录按 `REBUILD.md` 运行 `npm ci` 重建。排除项在清单和恢复生成的 `REBUILD.md` 中带重建方法。`pairing/` 含外部配对 runner 信息，默认不进入备份，需在新环境重新配对（`--include-pairing` 需所有者自行评估敏感性）。`conversations/` 与 `artifacts/` 可能包含私有内容，计划阶段会明确告警。
- 恢复目标必须是空目录；脚本先校验清单再复制，拒绝覆盖已有数据。恢复时会把数据库实体中指向旧数据目录的绝对路径（任务工作副本、artifact blob 等）改写为新目录，并更新恢复清单；数据库外的项目源路径保持不变。恢复后的在途执行进入 `reconciling`，只能“重新读取回执”，不要重跑、删除锁或改数据库；配对与依赖按 `REBUILD.md` 重建。历史事件/命令文本中的旧路径作为审计记录保留，不改写。
- `prune-data.mjs` 只做 dry-run：按目录树内最新修改时间（跳过可重建的 `node_modules`/`.git`）列出超过保留期限的 `workspaces/`、`reviews/`、`integration/`、`diagnostics/` 副本及空间；仍被未完成任务、运行中执行、待清理占位或在途集成的 task/integration ID 引用的目录会标记保护，不会出现在可清理列表。只读打开 WAL 数据库后，SQLite 可能在数据目录留下 `-shm/-wal` 辅助文件（例如 32 KiB 的 `-shm` 与 0 B 的 `-wal`）；业务数据不被修改。实际删除仍由所有者按现有授权流程执行。
- 备份与恢复目标都会用 realpath 检查，拒绝备份目标位于数据目录内或恢复目标位于备份目录内。备份为整文件读入内存（单个文件大小未额外限制，超大文件会占用等量内存），不保留原始 mtime/文件模式；恢复后的文件按私有内容权限写入。首版仅支持当前本机数据目录，不包含云备份、跨设备同步、源项目仓库、认证文件或外部模型配对令牌。

## 异常恢复

### Git 集成

自动合入使用 Windows Job Object。缺少已验证的进程容器时，自动合入在启动 Git 集成命令前停止。

- 排队中的任务可直接暂停或取消。候选准备或检查已经开始时，立即暂停、取消和宿主关闭会请求停止自有进程树。清理确认后才释放占位。优雅暂停允许当前集成完成，并暂停接续调度。
- 最终 fast-forward 启动前核对任务代次、停止意图、租约、项目授权、目标分支和 HEAD。命令启动后等候有界结果。Git 已合入时，任务记录实际提交与同期停止请求。
- 重启时用持久集成记录、进程清理回执及 Git 分支历史核对实际结果。若证据不足，任务进入“核对中”，可用“重新读取回执”再次检查。确认已合入的提交直接补录，保留当前 Git 内容。

### 模型执行

`reconciling` 表示旧执行或副作用尚不能确认。任务详情“核对中断执行”里的操作是“重新读取回执”：它按该次执行的完整身份重读 `<dataDir>/paired-runs/` 下的逐次回执，不释放未知占用，也不派发新执行。身份由 provider、model、attemptId、contextKey、generation、kind、persistent 和 runtime 组成；回执为 `<runKey摘要>.json`，执行锁为同名 `.json.lock`。进程是否存活、根进程是否退出或宿主是否重启，都不能代替清理确认。

- 身份全部匹配、终态 `completed`、结果完整、清理已确认且没有锁：恢复已有结果并按原验收与收集流程入库，不再次调用模型。
- 身份匹配、终态 `stopped`、清理已确认、没有完整结果且没有锁：允许按现有调度重试。
- 执行中、锁仍存在或无法读取、清理未确认、回执缺失或损坏、身份错配、终态矛盾：继续保持 `reconciling` 和资源占位，不自动重试、不自动修复。
- 完成回执已写入但业务入库中断：先按回执补完入库，不重复执行。

人工查看日志和工作副本只用于定位问题。没有“人工勾选已停止即释放占位”的入口；不要删除锁、改数据库状态或清理 `paired-runs` 来绕过核对。旧版本执行缺少完整身份和逐次回执时无法由 contextKey 推测结果，缺失回执也按未知处理，不因宿主重启或进程已退出而放宽。手动检测和聊天同样逐次留回执，尚无独立处置入口，未知时只能保守保持。

若主机权限导致 Windows Codex 工具初始化失败，检查专用 CODEX_HOME、运行身份和 Codex 沙箱环境；ACMS 会记录错误，但不会自行提升系统权限。

候选合并失败时，源项目保持不变。查看任务阻塞与保留的 candidate 目录；修复项目冲突、调整范围或检查后恢复。当前版本不会自动替所有者选择有歧义的合并策略。

更新源码时先暂停执行再重启宿主；不要在真实任务运行中覆盖 provider 核心文件。UI 修改后重新 build 并刷新 DSH。

## 卸载

```powershell
pwsh -File .\scripts\uninstall.ps1 -TargetProfile desktop
```

可用参数：
